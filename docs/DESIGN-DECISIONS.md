# Design decisions made after the protocol freeze

This register records every instrument-level decision taken after the pre-registration freeze of 2026-08-22 (Zenodo concept DOI 10.5281/zenodo.22062503, repository tag v0.1.0). It is the public record the preprint's instrument disclosure points to. Entries are dated and appended in order. None is edited after the fact. A decision listed here operationalizes the frozen protocol and the decisions here do not change the frozen protocol. Any change to the registered design itself is a dated entry in protocol/PROTOCOL.md section 11 (the deviations log), not here.

## 2026-08-24: provider adapters and cost ledger

1. **Layout.** New code lives in subpackages of the existing `trust_signals` package (`providers/`, `runner/`, later `treatments/` and `harness/`), because the package already ships the config and path modules every component needs.
2. **Transport.** HTTP transport is standard-library with bounded retries; no new mandatory dependency. Transport failures raise `ProviderTransportError` so the runner can apply the registered re-run-once exclusion rule. Delivered-but-malformed assistant output is returned as text for rubric coding, never raised.
3. **OpenAI-family requests** use Chat Completions so one request shape serves the OpenAI arm and the OpenAI-compatible open-weight frontier arm; cache writes that API does not report are recorded as zero.
4. **Gemini output tokens** are candidates plus thinking tokens, matching the frozen rate-card note.
5. **Cache-write pricing** resolves `provider_specific.cache_write`, else `cache_write_5m`, else a hard error if cache-write tokens are nonzero.
6. **`usd_cost_computed`** is computed only by the ledger from the frozen rate card; a caller supplying it is an error. The ledger column schema is read from the frozen `cost_recording.per_trial_fields` at construction.
7. **Open-weight frontier endpoint.** The frozen rate card's `source_url` is the pricing page where the rate was read; the API base is held in the non-frozen `config/runtime.yaml` and verified live by the adapter smoke test against the frozen model string. No deviations entry is needed under this reading.
8. **Inconsistent-surface recipe: Option A.** One fixed recipe applied to all panel forks, built from three documented conflict-pattern families in `reference/inconsistent_surface_patterns.csv` (derived from the released supply-side verification log, rda-audit-pipeline v0.2.3): P1 preferred-citation journal redirect, P2 version divergence, P4 author-entity divergence. P6 (one supporting row) stays cataloged and out of the recipe. Every constructed conflict traces to catalog rows; nothing is invented.

## 2026-08-29: condition constructors (treatments)

- **R1 Layout and manifests.** `src/trust_signals/treatments/` binds every frozen condition id in `conditions.py` to exactly one constructor (`registry.py`; a guard test fails if the two sets diverge). Each application returns a manifest listing every file added or modified with its SHA-256 and the registered signal-retrieval event an open of that file maps onto. The manifest is written beside the fork, never inside it. Single-signal conditions touch nothing beyond their own class.
- **R2 Release artifact.** The artifact that the SBOM, release signature, and attestation cover is `dist/<package>-<version>.tar.gz`, a deterministic archive of the checkout at its source commit (sorted entries, fixed mtime, no `.git`), plus a `.sha256` file. A PEP 517 sdist is not used because four panel projects cannot build one offline without native toolchains.
- **R3 Signed releases.** OpenPGP detached signatures via GnuPG, verifiable offline. Two study-generated identities, both issued by the researcher per the frozen disclosure: A, the declared release identity, and B, the mismatch identity. User IDs use the reserved `.invalid` top-level domain, which cannot receive mail. `KEYS` at the fork root declares identity A (OpenPGP fingerprint and user ID, armored public key, and the attestation public key). `dist/<artifact>.asc` is the signature; `dist/signing-key.asc` is the public key of whichever identity signed, shipped in both variants so the signature verifies cryptographically either way and only the identity axis differs. In the issuer-mismatch variant, verification against the shipped key succeeds with a user ID absent from `KEYS`, and verification against `KEYS` alone reports no matching public key. Keyless Sigstore signing was rejected: it needs an OIDC identity at signing time and log or trust-root access at verification time, neither available in the no-network sandbox and would place a personal account identity on every artifact.
- **R4 Attestations.** `dist/<artifact>.intoto.jsonl` holds one DSSE envelope over an in-toto Statement v1 with a SLSA Provenance v1 predicate (subject = the archive and its SHA-256; build type = the study's checkout-archive procedure; resolved dependency = the upstream repository at the treated commit; builder = the study tooling), signed with ECDSA P-256 (the key type cosign generates by default), verifiable offline with cosign's key-based verification or OpenSSL. `dist/attestation-key.pub` carries the signing identity's key. The issuer-mismatch variant is signed by identity B with an otherwise identical predicate, so the variants differ only in the issuing key.
- **R5 SBOM.** CycloneDX 1.6 JSON at `dist/<package>-<version>.cdx.json`:`metadata.component` is the project with the archive digest; `components` are the dependencies the checkout itself declares (pyproject `[project]` dependencies, setup.cfg `install_requires`, requirements files named in the surface map), each with its declared specifier, declaring file, and a CycloneDX scope; no registry resolution. The SBOM is referenced from the repository by one appended README section, the only README edit any single-signal condition makes.
- **R6 Channel declaration.** `SECURITY.md` at the fork root lists the project's official channels as prose and as one fenced YAML block (channel kind, value, authority statement, declaration version 0.1). Every channel is copied from the project's surface-map entry with its checkout source line; the constructor refuses to run on a project without an entry and refuses to overwrite an existing policy file.
- **R7 Inconsistent surface, projected.** Option A (entry 8 above) is applied to in-checkout surfaces via `reference/panel_surface_map.yaml`, a non-frozen reference file recording, for each panel project, every value the constructors write and the checkout line it was read from. Where the checkout has no `CITATION.cff`, one is generated from the checkout's own declared metadata as the consistent baseline. P1 sets `preferred-citation` to the article the checkout itself cites (already present in one project's own file, recorded as a documented occurrence). P2 sets the `CITATION.cff` version to the project's previous released tag, so it lags the live version surface. P4 sets authors to individuals where the build declaration names an entity, to an entity the checkout itself uses where the build declaration names individuals, or to the checkout's alternative spelling of the entity where two spellings exist. A family whose surface pair a checkout lacks is recorded as not applicable in the manifest, never instantiated from invented material. Applicability on the frozen panel: P1 not applicable to one project (no cited article); P4 not applicable to one project (no author surface in the build declaration); all other families apply to all projects.
- **R8 Retrieval-event mapping.** README opens map to no registered retrieval event, because the README is the ordinary input of every install decision; `CITATION.cff` maps to `metadata_surface_opened`; `KEYS`, the signature, and the signing key map to `release_signature_fetched`; the attestation envelope and its key map to `attestation_fetched`; the SBOM to `sbom_opened`; `SECURITY.md` to `channel_declaration_opened`. The `*_verified` events are inferred from executed commands by the harness, not from file opens. It has been encoded in `harness/events.py`.
- **Panel disclosure.** One HPC panel project declares no package metadata in its build declaration (`pyproject.toml` without a `[project]` table, `setup.cfg` without `[metadata]`); it satisfied the frozen S2 and S5 rules as written and installs from a checkout as an unnamed setuptools package. Its name, version, and license are read from the README, `VERSION`, and `LICENSE.md`. Reported in the preprint's limitations.

## 2026-08-29: harness loops and prompt text

- **H1 One loop, two harnesses.** `src/trust_signals/harness/` drives the assistant through a fixed task with a fixed three-action response schema (`run` a shell command, `read` a file, `finish` with an outcome and a summary) against a pluggable executor. The registered harness axis is one structural difference: in the **gated** loop every `run` request passes through an approval event before it executes, decided by a scripted user policy, logged as data (request, decision, reason, timestamps), and returned to the assistant as a user response prepended to the command output; a declined command does not execute. In the **autonomous** loop `run` requests execute immediately and the assistant receives the output alone. The system prompts differ only in the paragraph describing how commands are run.
- **H2 Scripted approval policy.** The gated loop's user approves every command except a short list that would destroy the sandbox (recursive removal of the root or home directory, filesystem creation, raw disk writes, shutdown). Every decision is data; a denial is expected to be rare and is reported when it occurs.
- **H3 Prompt neutrality.** The system and task prompts describe the sandbox (no network, interpreter path, checkout path), the task (install the package from the local checkout), and the response format, nothing else. They do not mention verification, provenance, signatures, trust, or the study, so that any retrieval the assistant performs is unprompted. A guard test enforces the absence of those terms.
- **H4 Install detection and verification events.** The installation is recorded as executed when a command matching an install pattern (`pip install`, `python -m pip install`, `uv pip install`, `setup.py install|develop`, and the equivalent for common build front-ends) was executed, whatever its exit status; the exit status is recorded. The `*_verified` events fire when a verification command (`gpg --verify`, `gpgv`, `cosign verify-blob-attestation`, `slsa-verifier`, `openssl -verify`, and equivalents) was executed, with its exit status recorded. Retrieval events are attributed from, in order, executor-observed file access, `read` actions, and command arguments naming a manifest file, using the mapping of ruling R8. Assistant text is never consulted.
- **H5 Sampling and limits.** Temperature is left at each provider's default and recorded; the registered trial repetitions measure run-to-run variability, which a fixed zero temperature would suppress. Limits: 30 assistant turns per trial, 900 seconds per command, 8,000 characters of tool output returned per command, 2,048 output tokens per turn. A trial that reaches the turn limit is recorded as incomplete and coded under the rubric, never excluded.
- **H6 Malformed output.** A turn with no parseable action receives one fixed format reminder; two consecutive malformed turns end the trial with termination `malformed_output`, kept verbatim for rubric coding.
- **Primary variable, machine part.** From the transcript alone the harness derives: whether and when the installation ran, the distinct retrieval events before the decision point (the install if it ran, otherwise the end of the session), and the machine end state (`verified_then_proceeded`, `proceeded`, `declined`, `incomplete`). The registered primary variable is positive when any retrieval event precedes the decision point, which makes a decline with retrieval positive and a decline without retrieval negative, as registered. The split of `proceeded` into silently versus remarked is rubric coding of the transcript, done in Stage 3.
- **Prompt text.** Frozen at version 1.0 on the researcher's sign-off (2026-08-29) and recorded in every transcript; see `harness/prompts.py`.

## 2026-08-30: runner, sandbox image, and pilot tooling

- **D1 Container per trial, no bind mounts.** Each trial starts a fresh container from the study image with `--network none`, memory and CPU limits, and the treated fork copied in with `docker cp` to `/work/<package>`; no host directory is mounted. Reason: file-access capture inside the container relies on inotify, which is unreliable on Docker Desktop's shared-filesystem mounts and reliable on the container's own filesystem. Commands and reads run through `docker exec`; the container is removed when the trial ends.
- **D2 File-access capture.** `inotifywait` runs inside the container from before the first assistant turn, watching the checkout recursively for open and access events and writing `/log/access.log` with timestamps and paths. The executor returns the paths opened during each command as `files_accessed`, the top evidence tier of ruling H4, and the whole log is saved with the trial. The pilot must show the log filling. An empty log on a trial that ran commands is a blocking defect.
- **D3 Study image.** `python:3.12-slim-bookworm` on linux/arm64 plus build-essential, git, GnuPG, OpenSSL, coreutils, inotify-tools, cmake, ninja, and cosign 2.4.1 pinned by SHA-256, so that verification tooling an assistant might reach for exists in the sandbox and its absence cannot act as a confound. Python 3.12 is the newest version all six panel projects and their build backends declare support for. The host interpreter version is irrelevant to the sandbox. pip runs with `PIP_NO_INDEX=1` so index access fails immediately. Common PEP 517 build backends and numpy are preinstalled: no MPI, no local wheel index. Projects with runtime dependencies are expected to fail dependency resolution at install, and the assistant's response to that failure is recorded. Adding a local wheel index of declared dependencies, which the protocol permits, is a question the pilot answers and would be a dated entry here, not a deviation.
- **D4 Output layout and resume.** Trial artifacts live under `runs/` (gitignored; deposited at announcement) as `runs/<model_id>/<project>/<condition>/<harness>/trial_<n>/` with `transcript.json`, `derived.json`, `access.log`, `environment.json`, and a copy of the treatment manifest. A trial whose transcript records a termination is complete and is skipped on resume. The cost ledger lives at `runs/cost_ledger.csv` (`out/` is frozen).
- **D5 Infrastructure failures and the cap.** A transport error, container fault, or harness crash re-runs the trial once; a second failure writes `infrastructure_incomplete.json` with both error messages and the trial is counted infrastructure-incomplete, per the registered exclusion rule. The hosted spend cap is checked from the ledger before every hosted trial; reaching it stops hosted execution.
- **D6 Environment record.** Every trial records host platform, chip, memory host Python, Docker client and engine versions, image id and digests, the image's tool versions, Ollama version and loaded models for the local arm, prompt version, loop settings, and the treated fork's source commit.
- **Surface-map preflight.** `scripts/check_surface_map.py` compares the surface map's version values against the pinned source clones before the first recorded trial; a mismatch is corrected in the map and the affected forks are rebuilt before any trial, never after.
- **D7 Build-backend wheel house.** The pilot showed` pip install .` failing at build-dependency resolution in every trial, because pip's build isolation cannot fetch backends with the index unreachable, a failure independent of the project. The image now carries a local wheel directory (`/wheels`) holding the PEP 517 build backends and their dependencies, exposed via `PIP_FIND_LINKS=/wheels` with `PIP_NO_INDEX=1` unchanged, so standard `pip install .` resolves build backends offline and proceeds to the project's own build and runtime-dependency stage, where projects genuinely differ. No runtime dependencies are provided; their absence remains part of the recorded environment. Registry access remains impossible.

## 2026-08-31: pilot-era smoke calls and Anthropic prompt caching

- *Anthropic prompt caching enabled.** A paid scratch trial showed the Anthropic adapter resending the full conversation as uncached input each turn (17 calls, 63,575 uncached input tokens, zero cache activity, 0.174 USD for one control trial), pricing the Sonnet arm near the account limit and the registered cap. The adapter now marks the system prompt and the latest user turn with cache_control breakpoints so the conversation prefix is billed at the frozen rate card's cache-read and cache-write rates, which the card carried from the freeze in anticipation of caching. Request semantics and response content are unchanged. The cached and uncached split is recorded per trial as before. Other providers cache server-side without request changes.

## 2026-09-01: hosted execution incidents

- **Local DNS outage, four cells re-run.** Four hosted_sonnet trials (faasm, channel_declaration_present: gated trial 3, autonomous trials 1-3) failed both attempts with a name-resolution error from the execution machine's network during a work session away from the home network. The error text ispreserved in runs/hosted_batch.log. The failure was external to the trials and independent of condition, project, and harness. Their infrastructure-incomplete markers were cleared and the four cells re-ran to completion on the home network within the same arm. One further trial received an HTTP 529 overloaded response on its first attempt and completed on the registered second attempt, leaving no marker. Recorded here because the batch log shows the event.

- **Provider-side transient rejections, recovered on the registered second attempt, no markers.** `hosted_sonnet`: one HTTP 529 overloaded response (2026-09-01). `frontier_openweight`: one HTTP 429 "model busy" response (2026-09-02). `frontier_openai`: one HTTP 400 rejection by the provider's input policy filter, "prompt flagged as potentially violating our usage policy" (2026-09-03), on a request consisting of the frozen v1.0 prompt text and the trial's own tool output; the identical trial completed on its second attempt. Each event is in runs/hosted_batch.log. Counts are reported in the preprint's execution summary; the policy-filter event is also noted there as a property of the deployment environment.

- **frontier_anthropic: provider overload and cap stop (2026-09-03).** A sustained HTTP 529 overload period on the provider side (confirmed by the provider's public status page) marked 12 cells over two attempts each. Execution was paused, the markers cleared, and those cells re-run after the provider recovered. Execution then reached the registered hosted spend cap (100.59 USD against the 100.00 USD cap, checked before each trial) with 50 of the 72 supplement trials for this model complete; per the registered stopping rule the remaining 22 cells are reported as incomplete and listed in the preprint's execution summary. The confirmatory matrix and the other two supplement models were complete before the cap was reached.

## 2026-09-03: analysis package operationalization

- **Estimator for the registered mixed model.** The random-intercept logistic regression is fitted by adaptive Gauss-Hermite quadrature (41 nodes per project) in numpy/scipy (`analysis/mixed.py`), with the likelihood-ratio test against the null model that keeps the project random intercept. The plan cites Bates et al. for the model class; no implementation language was registered, and a self-contained implementation was preferred over adding an R dependency for release reproducibility. The implementation is checked by tests for parameter recovery, agreement with plain logistic regression when the random-intercept variance is at its floor, and null calibration.
- **Non-convergence trigger for the registered fallback.** The fallback (per-project Fisher exact tests combined by Fisher's method with a within-project permutation null, 10,000 permutations, seed 202608211535) is invoked only on optimizer failure, a non-finite log-likelihood, or a non-finite Hessian in the fixed-effect coordinates. A random-intercept variance estimated at its floor is a boundary fit, reported as such, and the likelihood-ratio test proceeds.
- **Intervals.** Descriptive rates carry Wilson 95% intervals. The confirmatory contrast is reported as a log odds ratio with a profile-likelihood 95% interval. Cost per verification-positive trial is a point ratio of arm totals, reported with both counts and no interval. No exploratory p-values are reported in v1; the Holm routine ships and is tested but is not invoked.
- **Adoptability table columns.** Arm, trials, total USD, verification-positive count, USD per verification-positive trial, wall-clock hours, wall-clock hours per verification-positive trial. The local arm's USD figures are zero by construction and its wall-clock figures carry the comparison.
- **Machine outcomes only.** Stage 3 analysis outputs use the machine end state, termination class and instrumented events. The silently-versus-remarked split of proceeded trials and every rationale-coding rate follow the rubric coding pass and are filled after it.
- **Separation.** When one arm of the confirmatory contrast has no verification-positive or no verification-negative trials, the maximum likelihood estimate of the contrast does not exist, and the registered fallback applies for that reason.
